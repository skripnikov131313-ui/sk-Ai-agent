# Требования и зависимости задач

Для каждой задачи основной очереди задаётся `target`. Выбор явный: Agent не угадывает требования по словам в тексте. У старых задач без этого поля используется `current`.

| Значение | Где разрешён запуск |
| --- | --- |
| `current` | В текущей среде; дополнительных требований к ОС нет |
| `windows` | В процессе Agent на Windows (`win32`) |
| `windows-gui` | На Windows с явно заявленным доступом к рабочему столу (`--desktop`) |

`--desktop` допускается только на Windows. Это заявление оператора для конкретного процесса Agent, а не проверка GUI-инструментов и не подключение к компьютеру. Codex по-прежнему работает с `workspace-write`; если необходимых инструментов нет, он должен вернуть `blocked`. Настройки sandbox, сетевые права и авторизация флагом не меняются.

## Панель

В форме задачи выберите «Где выполнять» и при необходимости одну предыдущую задачу в поле «После задачи». Её статус должен стать `completed`, прежде чем новая задача сможет стартовать. В карточке ожидания указана причина; счётчик попыток остаётся нулевым. В сведениях видны требования и предшественники. Над очередью показана ОС именно её текущего исполнителя.

Непустой список `blockers` в корректном свежем отчёте переводит задачу в `blocked`, даже если исполнитель одновременно объявил `completed` или `failed`. Исходный отчёт сохраняется для диагностики; статус задачи определяет Agent. Для старой записи `completed` с блокерами в отчёте зависимые задачи также остаются в ожидании. Такая история не переписывается автоматически.

Для явно выбранной работы с рабочим столом Windows запуск панели выглядит так:

```powershell
.\agent.cmd ui --open --desktop
```

Запуск очереди берёт конечный список `queued` и `waiting`. Недоступные задачи не вызывают Codex и не мешают независимым. После успеха предшественника его зависимости снова проверяются, и готовые задачи этого снимка выполняются в том же запуске. Если остались только недоступные задачи, запуск завершается с состоянием `waiting` и освобождает lock. Он не опрашивает бесконечно выключенный ПК. При реальном блокере или отсутствующем отчёте сохраняется прежняя остановка запуска.

Задачи, добавленные позднее, требуют следующего запуска. После завершения batch смена среды сама не запускает очередь: требуется запуск Agent с доступом к той же очереди и явная команда выполнения. Межмашинной доставки здесь нет.

## CLI и API

Параметры `add` указываются до текста. `--after` можно повторять; максимум 32 существующих UUID из этой же основной очереди:

```powershell
.\agent.cmd add --target windows "Проверить Windows API в проекте"
.\agent.cmd add --after <UUID-предыдущей-задачи> "Проверить полученный результат"
.\agent.cmd run <UUID-задачи>
.\agent.cmd run <UUID-GUI-задачи> --desktop
```

Для Linux используются те же аргументы после `node src/cli.mjs`. Недоступный прямой `run` сохраняет `waiting` и возвращает код 3 без расхода попытки. `resume` повторно проверяет требования и при несовместимости сохраняет прежние статус, session ID и число попыток. Проверка находится в адаптере исполнения, поэтому обход формы панели её не отключает.

`POST /api/tasks` принимает только `goal`, `requestId`, `target`, `dependsOn`. Повтор отправки с тем же идентификатором сравнивает текст и нормализованные требования; изменение любого из них требует нового идентификатора. UUID зависимостей приводятся к нижнему регистру, сортируются, дубликаты удаляются. Предшественник должен уже существовать; HTTP-операции изменения зависимостей нет, поэтому через поддерживаемый API цикл создать нельзя. Отсутствующий или незавершённый предшественник не разрешает исполнение. Основная очередь и `work` имеют разные базы; ссылки между ними не поддерживаются.

## Markdown-план

Для `work` требования указываются в начале текста пункта:

```markdown
- [ ] Исправить переносимую логику и проверить её тестами.
- [ ] [windows] Проверить native API на Windows.
- [ ] [windows-gui] Проверить поведение настоящего окна.
```

Без метки используется `current`. Независимые доступные пункты продолжаются после ожидающих. Для GUI-пунктов на Windows нужен `work --desktop` либо `work-start --desktop`. Текст метки сохраняется при отметке `[x]`; изменение текста или метки создаёт другую идентичность пункта. Произвольные зависимости Markdown-плана не вводятся: он по-прежнему состоит из независимых пунктов. Итог `waiting` имеет код 3, прогресс сохраняется, повторный запуск без изменения доступности не расходует попытки.

## Что подтверждено

Node-тесты проверяют требования на уровне store, прямого runner, HTTP queue и `work`; Chromium проверяет выбор среды, зависимость, сохранение черновика и понятное ожидание. Исполнитель в этих тестах — локальный протокольный имитатор, без модели. Внедрённый тестовый профиль Windows проверяет ветвление кода, а не настоящий desktop. Реальное выполнение через панель, Windows GUI и передача задач Cloud ↔ ПК остаются отдельной приёмкой и не подтверждаются этим этапом.
