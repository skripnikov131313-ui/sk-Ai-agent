# Работа по плану одним запуском

`work` управляет последовательными вызовами официального Codex CLI. После завершения одного вызова диспетчер проверяет пункт и переходит к следующему без нового сообщения пользователя. `local` остаётся отдельным интерактивным клиентом.

Windows: `agent.cmd work`, Linux: `node src/cli.mjs work`. Для отдельного фонового процесса — `agent.cmd work-start` / `node src/cli.mjs work-start`; двойной щелчок по `work.cmd` в Windows также запускает фон. Используются установленный native Codex и существующая авторизация/квота. Установка ПО, копирование токенов или входящие сетевые порты не требуются.

## План и пределы

- Источник по умолчанию — `TASKS.md`. Другой Markdown-файл внутри проекта: `agent.cmd work PLAN.md --minutes 90`.
- Исполняются пункты верхнего уровня `- [ ] текст` или `* [ ] текст`. Отмеченные пункты, вложенные списки и примеры в code fences не запускаются. Пункты считаются независимыми; план с зависимостями сначала нужно разбить на разрешённые независимые работы.
- Метки `[windows]` и `[windows-gui]` в начале текста пункта задают требования. Недоступные пункты сохраняются как waiting без вызова модели и расхода попыток; доступные продолжаются. Для рабочего стола нужен явный --desktop на Windows. Если остались только недоступные пункты, work завершает процесс с кодом 3. [Контракт маршрутизации](TASK_ROUTING.md).
- Список фиксируется в начале запуска: весь исходный план. Новые пункты, добавленные моделью, не продлевают запуск. План содержит не больше 100 пунктов и 64 КиБ. Необязательный --max-tasks позволяет пользователю явно выбрать меньшую часть.
- Общего таймера по умолчанию нет. Необязательный `--minutes` задаёт положительное число минут без прежнего ограничения в четыре часа. Попытка — до 10 минут и оставшегося явно заданного бюджета; всего до трёх попыток на пункт. `paused` означает выбранный лимит числа пунктов, `interrupted` с exit 124 — заданный лимит времени, exit 130 — остановку пользователем.
- `blocked` сохраняется без бесконечных повторов; остальные независимые пункты продолжаются. После устранения причины можно явно выбрать `--retry-blocked`; общий предел трёх попыток сохраняется.
- Повтор после timeout либо явного failed-отчёта использует сохранённый session ID. При отсутствии корректного отчёта, например при ошибке запуска/авторизации/квоты, запуск прекращается и следующие вызовы не расходуют квоту. Точная причина и остаток квоты автоматически не определяются.

## Приёмка и сохранение

Для принятия пункта нужны свежий structured report со статусом completed, непустой `checks`, отсутствие blockers и отметка `[x]` исходного пункта без изменения его текста/раздела. Это проверка согласованности плана и модельного отчёта. Правильность произвольного изменения она не доказывает: проверки выполняет Codex внутри своего sandbox, результаты сообщает модель. Отдельная команда `smoke` дополнительно независимо проверяет содержимое контрольного файла.

Идентификатор пункта зависит от пути плана, раздела и текста. Уже принятые пункты не выполняются повторно, даже если checkbox случайно снят. Завершённая попытка, не успевшая пройти приёмку до сбоя, проверяется при следующем запуске. Exit code клиента сам по себе не подтверждает результат.

Состояние и проверки: `.skai-agent/work/tasks.json`, отчёты попыток — рядом в `runs`. Фоновый worker сохраняет `service.json`, журнал и отдельную конфигурацию в `services/<id>`. Они исключены из Git; конфигурация содержит только параметры работы, без копирования credentials. `agent.cmd work-status` показывает состояние процесса и очереди.

Ctrl+C останавливает foreground worker и не запускает следующий пункт. Для фона `agent.cmd work-stop` сохраняет запрос остановки конкретному worker: тот прерывает native child и сохраняет очередь. Это работает и в Windows, где принудительный SIGTERM самого Node не гарантирует остановки потомков. `work-start` не зависит от stdin или открытого терминала. Второй процесс отвергается; неизвестный/живой/чужой worker не восстанавливается автоматически. После аварии нужны `work-recover` и новый `work` либо `work-start`. Предел попыток при этом сохраняется.

## Граница автономности

Отдельный worker продолжает после выхода запускающего процесса, пока жива исполняющая машина. В Windows компьютер должен быть включён. В Cloud он зависит от жизненного цикла managed environment: фоновый процесс не гарантирует восстановление после приостановки. Он выполняет утверждённый план независимо от новых ходов чата; сам интерфейс чата программой не меняется. Внешний scheduler, который поднимает новую машину после приостановки, не развёрнут.

2026-11-15 пользователь применил доступ к chatgpt.com в текущей машине: observed revision=2, сеть enforced, новый HTTPS-запрос вернул 200. Официальный `codex cloud list` дошёл до сервера и получил 401 с требованием повторного входа. Сетевой 403 для этого домена устранён; авторизация требует отдельной проверки.

Реальная попытка двух файловых задач остановилась до создания proof-файлов. В обычном command sandbox служебный каталог Codex read-only, в том числе при --ephemeral. Штатный разрешённый запуск снаружи command sandbox позволил инициализировать CLI; сами задачи при этом сохранили --sandbox workspace-write и корень проекта. Следующим подтверждённым блокером стала авторизация: native CLI создал thread, но вернул turn.failed с сообщением о невозможности обновить access token и требованием войти заново. Это не успешная модельная приёмка.

Для штатного codex login --device-auth нужен auth.openai.com. Его запрос пока получает CONNECT 403. Домен добавлен в сетевой черновик с сохранением остальных правил, инструмент вернул requires_publish=true. Доступ нужно применить к текущей машине, а публикация сохраняет конфигурацию будущим задачам. Новые соединения, повторный вход через официальный клиент и реальная файловая приёмка необходимы до запуска основного плана. Tokens/auth-файлы не копируются в проект или конфигурацию среды.

Изменения Cloud-репозитория сами не обновляют копию на ПК. Непрерывная работа новой версии на конкретном ПК отдельно не подтверждена. Автоматические проверки исполняют fixture CLI без модели, в том числе в Windows CI.

## Ограничения прав

Автопереходы и ограниченные повторы включаются выбором `work`; обычные `run/resume` не меняют поведения. Каждый вызов использует `workspace-write`, корень проекта, native CLI без shell и фильтр журналов. Содержимое плана не предоставляет полномочий на системные установки, публикацию, расходы или выход за пределы проекта. Диспетчер не выполняет команды из модельного отчёта вне sandbox, не хранит API-ключи и не открывает remote shell.

Модельный код может ошибаться; checkbox не является независимым тестом. Конечный список, timeouts, предел попыток и сохранённые отчёты ограничивают работу без прогресса. Перенос состояния между машинами, внешний scheduler и уведомления требуют отдельного проектирования.
