# Архитектура Agent

## Долгая работа

Codex Cloud — рекомендуемый диспетчер для задач, которые должны продолжаться при выключенном ноутбуке и быть доступны с мобильных устройств. Пользователь описывает задачу в поддерживаемом Cloud UI. Подготовленная среда содержит подключённые репозитории, зависимости и права. Не реализовать отдельный Cloud scheduler или скрытый webhook, пока не подтверждены официальные интерфейсы/лимиты.

## Локальная работа

Локальный Node CLI/launcher — ограниченный worker для Windows API, файлов и GUI. Он использует установленную Codex CLI авторизацию и исполняет задачу только при доступной локальной машине. Узкий сценарий не означает автоматическую синхронизацию чатов/памяти с Cloud.

## Ответственность

- Doctor: безопасная диагностика, без печати секретов.
- Task Store: устойчивая очередь задач и статус.
- Execution Adapter: отдельный Codex CLI процесс, root workspace и timeout.
- Reports: JSON schema и различение завершения/блокировки/ошибки.
- Memory: файлы проекта и журнал, без полагания на скрытый контекст чата.

Проектная память реализована в `src/memory.mjs`: versioned MEMORY.json с предпочтениями/проверенными приёмами, ограниченный контекст native попытки, fingerprint и ID записей в checkpoint/event log, метрики существующих очередей. Сырые отчёты автоматически не превращаются в правила. Просмотр доступен в CLI и read-only разделе панели; отсутствие каталога сохраняет прежнее поведение, некорректный каталог останавливает вызов до расхода попытки. [Контракт памяти](docs/PROJECT_MEMORY.md).

Первый локальный интерфейс Agent реализован в `src/web`: Node HTTP API, статическая панель и последовательный controller основной очереди. UI использует существующие Task Store и Execution Adapter. Нажатие запуска фиксирует список queued/waiting, общий таймер отсутствует, повторы ограничены и используют сохранённую сессию. Прогресс batch хранится атомарно в основной базе; новый UI-процесс читает очередь из файла. Диспетчер `work` сохраняет отдельный источник плана и отображается только для чтения.

`src/projects.mjs` управляет локальным реестром дополнительных Git корней: канонические root/gitDirectory, очищенная идентичность origin и стабильный scope. HTTP выбирает только известный ID/scope. Дополнительные очереди и отчёты хранятся централизованно в private data Agent, с projectBinding в базе. Перед попыткой runner повторно проверяет актуальный реестр и Git identity; скопированная или переназначенная очередь не принимается автоматически. Один сервер панели разрешает одну активную очередь среди проектов. Клиент разделяет черновики по scope и отбрасывает ответы прошлого выбора. Обычный CLI/work остаётся на корне Agent; межмашинный транспорт не добавлен.

`src/routing.mjs` проверяет явный target (current/windows/windows-gui) и зависимости от completed задач. Возможности исполнителя берутся из текущей платформы и явного Windows-флага --desktop. Недоступность даёт waiting до захвата native процесса, без расхода попыток. Проверка повторяется в runner для прямых run/resume; queue выбирает готовую задачу из конечного снимка после каждого успеха. Старые задачи без требований остаются current. API не позволяет менять требования уже созданных задач и ссылаться на ещё не существующие, что исключает циклы через поддерживаемые операции.

Интерфейс принимает только типизированные операции задач; root/command/worker profile не принимаются от HTTP-клиента. Loopback/Origin/Host/CSP защищают локальный UI от внешних страниц; удалённая аутентификация, iPhone-клиент, mobile notification и межмашинный транспорт ещё не реализованы. [Контракт маршрутизации](docs/TASK_ROUTING.md).

Для будущего Cloud ↔ Windows транспорта подготовлены [модель угроз, границы pairing/владения и матрица приёмки](docs/WORKER_THREAT_MODEL.md). Это проект требований до выбора поддерживаемого сервиса, не подключение ПК или скрытый scheduler.
